> Note: the share-token frontmatter field shipped as `shareToken` alongside the retained internal `token` id (cookie id), exactly per §1.1.

## 1. Access model

The gallery supports **three album access types**. This replaces the current implicit model.

| Type | Listed on /photos | How it's opened | Frontmatter |
|------|-------------------|-----------------|-------------|
| **Public** | yes | direct visit | (default) |
| **Password-protected** (client galleries) | yes, in "Locked" tab | password form → cookie | `password: "..."` |
| **Link-share** (unique URL) | no (hidden) | secret link `?token=...` | `shareToken: "<random>"` |

A password-protected album **may also** have a share token (client gets a link that skips the password form).

### 1.1 Requirements

- **R1.1 — Random tokens.** Share tokens are cryptographically random (≥ 16 bytes, URL-safe), generated by the admin panel. The current deterministic `sha256(albumPath)` token derivation is removed — a token must never be computable from public information.
  - Migration: one-shot script regenerates tokens for all albums that currently have one; old `generate-tokens.mjs` scheme retired.
- **R1.2 — Tokens are opt-in.** A `?token=` parameter is only honored for albums that explicitly have a `shareToken` set. Albums without one cannot be opened by token at all.
- **R1.3 — Signed access cookie.** The `album-access` cookie value is signed (HMAC-SHA256 with a server secret from `.env` → `ACCESS_SECRET`). Forged cookies are rejected. Existing flags stay (`httpOnly`, `secure` in prod, `sameSite: strict`, 24 h).
- **R1.4 — Media routes enforce access.** One shared `assertAccess(albumPath, cookies, token)` helper is used by **all** routes that expose photo data:
  - `src/pages/albums/[...path].ts` (originals)
  - `/api/thumbnail`, `/api/exif`, `/api/video-info`, `/api/watermark`, `/api/download-album`
  - Public albums keep today's behavior (no check overhead beyond a lookup).
  - `.meta/` paths are blocked at the Node layer, not only via `.htaccess`.
- **R1.5 — Download check includes ancestors.** `download-album` denies access when any password-protected ancestor is not unlocked (same resolution logic as the page).
- **R1.6 — Rate limiting works behind the proxy.** Client IP is taken from `X-Forwarded-For` (first hop) when the direct peer is loopback; failed password attempts are limited per real client IP. Invalid `?token=` attempts are rate-limited too.
- **R1.7 — Locked albums don't leak content.** The prerendered "Locked" tab on `/photos` shows a generic lock placeholder instead of the album's cover photo.
- **R1.8 — One access implementation.** The three parallel access-control implementations are reduced to one module (`src/lib/access.ts`); dead code (`PasswordProtection.astro`, `check-password.ts`, `check-access.ts`, dead exports in `albums.ts`) is deleted.

## 2. Gallery features

### 2.1 Client proofing (selection + comments)

Purpose: a client opens their (password/link-protected or public) gallery, marks the photos they choose, optionally comments on individual photos, and submits the selection. The owner reviews submissions in the admin panel.

- **R2.1 — Opt-in per album** via frontmatter `proofing: true` (settable from admin).
- **R2.2 — Selecting.** Each photo gets a select toggle (heart) in the grid and in the lightbox. A visible counter shows "N selected". Selection persists in `localStorage` per album so the client can come back later.
- **R2.3 — Per-photo comment.** A selected photo can carry a short text note (e.g. "this one in B&W"), editable from the lightbox and from a review panel.
- **R2.4 — Review & submit.** A "Review selection" panel lists chosen photos (thumbnails + comments), lets the client enter their name (optional) and submit.
- **R2.5 — Server storage.** `POST /api/proofing` stores the submission as JSON under the album's `.meta/proofing/` (timestamp + name + list of `{filename, comment}`). Requirements:
  - only accepted for albums with `proofing: true`;
  - the request must pass the same access check as the album (R1.4);
  - rate-limited; payload size-capped; filenames validated against the album's actual photo list.
- **R2.6 — Admin review.** Admin shows proofing submissions per album: submission list, selected photos as thumbnails with comments, copy-as-list (plain filenames) and CSV export. The album tree shows a badge when an album has submissions.

### 2.2 Tags & search

- **R2.7 — Clickable tags.** Tag pills on album pages link to a filtered view (`/photos/tags/<tag>`) listing all non-hidden albums carrying that tag.
- **R2.8 — Album search.** A search box on `/photos` filters albums live by title, description and tags.
- **R2.9 — Photo search.** A search page (`/photos/search?q=`) also finds individual photos by filename, capture date (EXIF), and camera model — powered by the metadata cache (R2.11), no external index. Results link into the album with the lightbox opened on the photo. Only content from **public** albums is searchable; protected/hidden album content never appears in results.

### 2.3 Performance & image quality

- **R2.10 — Right-sized thumbnails.** Grid tiles use `small` (400 px) with a `srcset` step to `medium` (1200 px); the lightbox uses `large` (1920 px); the "Original" toggle is unchanged. All grid/cover `<img>` get `loading="lazy"`, `decoding="async"`, and explicit `width`/`height`.
- **R2.11 — Metadata cache.** Per-album `.meta/index.json` stores `{filename, width, height, orientation, size, exifDate, camera, mtime}` (+ a tiny base64 blur placeholder). Invalidated per file by `mtime`. `getPhotosForAlbum()` reads the cache instead of running Sharp + exifr per request. Cover lookups on collection pages use it too.
- **R2.12 — Blur-up placeholders.** Grid images render the LQIP placeholder from the cache until loaded.
- **R2.13 — WebP.** Thumbnail endpoint serves WebP when the client's `Accept` header allows it, JPEG otherwise; cache is keyed by format. Quality/size stay configurable in one place.
- **R2.14 — Thumbnail correctness.** Thumbnail disk cache is invalidated when the source file's `mtime` changes. Failed generation returns the correct `Content-Type` and a short-lived cache header (no more caching a fallback for a year). Concurrent Sharp jobs are capped by a small semaphore.
- **R2.15 — Streaming ZIP.** Album download streams the archive (no full in-memory buffering server-side), with a configurable size cap and a clear error above it.

### 2.4 Slideshow

- **R2.16 — Slideshow mode.** The already-schema-valid `style: slideshow` works: opening the album starts a fullscreen auto-advancing lightbox. Any album's lightbox also gets a play/pause button (`S` key), configurable interval (default 5 s), pause on user interaction, disabled auto-play under `prefers-reduced-motion`.

## 3. Admin panel

### 3.1 Bug fixes (must-have)

- **R3.1 — No data loss on save.** `PUT /api/albums/*` merges into existing frontmatter instead of replacing it. The cover (`thumbnail`) select is populated on album load and never silently cleared or leaked across albums.
- **R3.2 — Video management works.** Video upload (button + drag-drop) and video delete are wired to real endpoints (`POST/DELETE /api/videos/...`).
- **R3.3 — `npm run update` is safe.** `update-albums.mjs` no longer deletes `body.md` (admin-authored album text survives all maintenance scripts).
- **R3.4 — Server hardening.** All admin routes resolve paths through one `resolveSafe()` guard (reject escapes from the content root); multer gets `limits` + `fileFilter` (images/videos only) and filenames are sanitized; a JSON error middleware handles multer/body-parser errors; upload collisions prompt instead of silently overwriting.
- **R3.5 — Deploy consistency.** `fix-server-paths.mjs` reads `DEPLOY_REMOTE_ROOT` from the environment (passed by `deploy.sh`) instead of a hardcoded path; `deploy.sh` gets `set -euo pipefail` and per-step failure handling.

### 3.2 Reorder & bulk operations

- **R3.6 — Photo drag-reorder.** Photos in the admin grid can be drag-reordered; order is stored as `photoOrder: [...]` in frontmatter, and the gallery's `sort: custom` actually applies it (today it's a no-op). Photos not in the list sort after, by name.
- **R3.7 — Album reorder.** Sibling albums can be reordered (drag in tree or up/down controls); writes the numeric `order` fields.
- **R3.8 — Home cards drag-reorder.** The existing `POST /api/home/cards/reorder` endpoint gets its UI.
- **R3.9 — Bulk photo operations.** Multi-select in the photo grid → bulk delete, bulk move to another album, set-as-cover.
- **R3.10 — Rename / move album.** New endpoint + UI to rename an album folder or move it under a different parent (with folder-name sanitization and thumbnail-cache move).

### 3.3 Deploy & tools from the admin

- **R3.11 — Script runner.** The Tools tab can run: deploy (sequential/parallel), build, sanitize, fix-broken-cards, clear thumbnails — with live streamed output (SSE), an explicit confirmation step, and a lock preventing concurrent runs. Exit status is shown clearly.

### 3.4 Editor experience

- **R3.12 — Upload progress.** Per-file progress bars and per-file success/failure results (XHR/fetch streams instead of a text swap).
- **R3.13 — Photo preview.** Click a photo in the admin grid to open a large preview with basic EXIF info.
- **R3.14 — Unsaved-changes guard.** Switching album/tab with unsaved form or editor changes prompts before discarding.
- **R3.15 — Correct share links.** The share-link builder uses the configured site URL (from config/env), not `origin.replace(':4444', ':4321')`.
- **R3.16 — Offline admin.** CodeMirror (and other CDN assets) served locally.
- **R3.17 — Proofing view.** See R2.6.

## 4. Engineering guardrails (done alongside phase 1)

- **R4.1 — Type checking.** `astro check` added as an npm script and required to pass.
- **R4.2 — Tests.** Vitest suite covering at minimum: access resolution (tokens, passwords, inheritance, cookie signing), path-traversal guards, metadata cache invalidation, `sort: custom` ordering, proofing payload validation.
- **R4.3 — CI.** GitHub Actions workflow: install → `astro check` → tests → build, on PRs and `main`.
- **R4.4 — Dead code removed.** Items listed in R1.8 plus the `deleted/` directory; `sharp` declared as a direct dependency; admin-only deps (`express`, `cors`, `multer`) documented as such.
